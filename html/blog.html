Product Thinking

Most product problems are subtraction problems in disguise.

Adding a feature is the easiest response to a complaint and the least likely to fix it. We keep coming back to the same discipline: find out what's actually blocking someone, then remove it.

  • Start from the workaround

    The spreadsheet someone built on the side is a better spec than any feature request.

  • Cut before you add

    Every new surface adds maintenance, explanation, and one more place for things to drift.

  • Make the state obvious

    If someone has to ask where things stand, the interface already failed.

Workflows & Systems

How a note becomes a note.

Our editorial process is the same loop we use for product work: start from a real question, write the smallest honest version, put it in front of someone, and keep only what survives.

  • It starts with a stuck moment

    Every note begins with something we couldn't figure out and had to work through.

  • Written, then cut

    The first draft is always longer. The useful part is whatever remains after the trimming.

  • Read by someone else first

    If a colleague can't follow it, the note isn't finished — it's just typed.

On pace

Slow down to go faster.

The week you spend framing the problem is usually the week you save three times over downstream. Speed in software isn't typing faster — it's throwing away fewer finished features.

  • Name the constraint: Define what not to solve so the core loop gets undivided focus.
  • Clickable reality early: Test assumptions with working prototypes before locking database models.
  • Reversible milestones: Ship modular releases that keep feedback immediate and rework cheap.
